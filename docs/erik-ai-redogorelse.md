# Individuell AI-redogörelse – Erik Alduaifi

Under Blue Team-projektet använde jag Claude och Claude Code som stöd i flera delar av arbetet: för att förstå nya tekniska begrepp, tolka felmeddelanden och ta fram förslag på Terraform-ändringar. AI användes som ett hjälpmedel och ett bollplank, inte som ensam beslutsfattare. Jag har hela tiden sett AI:s svar som förslag som behöver förstås, prövas och anpassas innan de används i vår miljö.

Mitt huvudsakliga användningsområde var OS Login på jumphosten. Innan projektet hade jag begränsad erfarenhet av hur åtkomst till virtuella maskiner styrs i GCP, och AI hjälpte mig att snabbt bygga upp en grundförståelse. Jag fick förklarat hur OS Login kopplar SSH-åtkomst till Google-identiteter i stället för till manuellt hanterade SSH-nycklar, samt skillnaden mellan rollerna `osLogin` och `osAdminLogin`, där den första ger vanlig inloggning och den andra även ger administratörsbehörighet (sudo) på maskinen. AI hjälpte mig också att förstå hur behörigheten kan tilldelas på instansnivå med `google_compute_instance_iam_member` i stället för på hela projektet. Det var viktigt för oss eftersom det följer principen om minsta möjliga behörighet: användarna får bara åtkomst till jumphosten och inte automatiskt till alla andra VM:ar i projektet. Jag använde även AI för att förstå skillnaden mellan Headscale/Tailscale, som ger nätverksåtkomst till miljön, och OS Login, som styr vem som får logga in via SSH och med vilken behörighet på själva VM:en. Att förstå att dessa två lager löser olika problem och kompletterar varandra gjorde det lättare att resonera kring vår säkerhetsmodell som helhet.

Jag använde också AI för att tolka fel från `terraform fmt`, `terraform plan` och CI. Felmeddelandena var ibland svåra att förstå på egen hand, och AI hjälpte mig att avgöra om problemet låg i syntax, formatering, saknade variabler eller i själva resursdefinitionen. Det gjorde felsökningen mer strukturerad och sparade tid. Dessutom använde jag AI som bollplank kring hur `terraform.tfvars` bör hanteras. Frågan var om filen skulle ligga i Git eller inte. Att sluta spåra filen minskar risken att verkliga eller känsliga värden hamnar i repot, vilket är ett vanligt och rimligt råd. Samtidigt behövde vårt CI-flöde filen för att kunna köra `terraform plan`, och när den togs bort slutade pipelinen fungera som tänkt. Filen återinfördes därför, och variablerna hanterades senare i deploy-workflowet i stället. Det var ett tydligt exempel på att ett generellt råd från AI inte automatiskt passar alla situationer, utan behövde anpassas efter hur vår pipeline faktiskt var uppbyggd.

Jag följde inte AI:s förslag utan att kontrollera dem. Alla ändringar granskades som Git-diff så att jag kunde se exakt vad som ändrats, kontrollerades med `terraform fmt -check` och `terraform validate` i PR-kontrollerna innan de mergades. Efter merge körde deployflödet `terraform plan`, som visade vilka resurser som skulle skapas, ändras eller tas bort innan de applicerades. Vid IAM-ändringar var jag särskilt noggrann med att kontrollera vilken roll som tilldelades, på vilken nivå och till vilka konton, eftersom ett felaktigt förslag antingen kan ge för bred åtkomst eller låsa ute användare som behöver komma in. I de fallen räckte det inte att koden såg rimlig ut, utan jag behövde förstå konsekvenserna av ändringen.

Min erfarenhet är att AI var mycket användbart för att snabbt komma in i nya områden som GCP IAM och OS Login och för att få struktur på felsökningen när något inte fungerade. Det gjorde att jag kunde lägga mer tid på att förstå och mindre tid på att leta efter information. Samtidigt har jag lärt mig att ett välformulerat och säkert formulerat svar ändå kan vara fel, föråldrat eller helt enkelt inte passa den egna miljön. Därför baserades de slutliga besluten på Terraform-kontroller, CI-resultat och teamets granskning snarare än på AI:s svar i sig. Jag ansvarar själv för de ändringar jag committade under projektet och jag kan förklara och motivera dem utan AI:s hjälp.
